# Database — `proxy/src/db.js`

## Purpose

`db.js` is the persistence layer, built on Node's built-in `node:sqlite` (no npm dependency; needs Node ≥ 23.4 as `package.json` states). It stores CTF records, every proxied request, every alert, the cross-CTF player identity map, dashboard accounts and sessions, and a small key/value table for admin state. Request and alert inserts are batched into one transaction every ~200 ms (or every 500 rows) so a fuzzing burst never stalls the proxy. Everything else is synchronous and direct.

## Where it sits

| | |
|---|---|
| Required by | `server.js` (creates `new Db(DB_FILE)`, `openCtf`, `endCtf`, `activeCtf`, `get`/`set`, `playerFor`, raw `stmts.upsertIdentity`, `close`); `store.js` (`addRequest`, `addAlert`, raw `db.db.prepare` for rename); `dashboard.js` (`flush`, `alerts`, `ackAlerts`, `studentDetail`, `runSql`, `exportCtf`, `importCtf`, `listCtfs`, `activeCtf`, raw `db.db.prepare` for ack-all and autocomplete values); `replay.js` (`requestsOf`); `auth.js` (accounts/sessions methods, `get`/`set`); `admin.js`, `approvals.js`, `decoy.js` (`get`/`set`) |
| Requires | `path`, `fs` (create the data folder), `node:sqlite` (`DatabaseSync`), `./util` (`log`) |

Several callers reach past the wrapper to `db.db` (the raw `DatabaseSync`) and `db.stmts`. Keep that in mind when renaming columns.

## Data it owns

### Table `ctfs` — one row per recorded event

| Column | Type | Meaning |
|---|---|---|
| `id` | INTEGER PK | CTF number shown in the dashboard and used in `ctf_id` everywhere. |
| `name` | TEXT NOT NULL | From `CTF_NAME`, the dashboard form, or `ctf-YYYY-MM-DD`. Imports get ` (imported)` appended. |
| `started_at` | INTEGER NOT NULL | Epoch ms. |
| `ended_at` | INTEGER | `NULL` while active. Set by `endCtf()`. |
| `imported` | INTEGER DEFAULT 0 | `1` for CTFs created by `importCtf()`; such rows are never considered "active". |

| Column | Type | Meaning |
|---|---|---|
| `id` | INTEGER PK | The `player_id` referenced by `identities` and `requests`. |
| `name` | TEXT NOT NULL | Display name at creation; never updated. |
| `created_at` | INTEGER NOT NULL | Timestamp of the first identity. |

| PK | `(kind, value)` | One player per identity value — the basis of cross-CTF matching. |

## Walkthrough

### Schema

```js
// lines 11-42 (excerpt)
const SCHEMA = `
CREATE TABLE IF NOT EXISTS ctfs (
  id INTEGER PRIMARY KEY, name TEXT NOT NULL, started_at INTEGER NOT NULL, ended_at INTEGER, imported INTEGER DEFAULT 0
);
...
CREATE TABLE IF NOT EXISTS identities (
  player_id INTEGER NOT NULL, kind TEXT NOT NULL, value TEXT NOT NULL, ctf_id INTEGER, first_seen INTEGER, last_seen INTEGER,
  PRIMARY KEY (kind, value)
);
...
CREATE INDEX IF NOT EXISTS requests_ctf_ts ON requests(ctf_id, ts);
CREATE INDEX IF NOT EXISTS requests_ctf_student ON requests(ctf_id, student);
...
CREATE TABLE IF NOT EXISTS kv (k TEXT PRIMARY KEY, v TEXT);
`;
```

- Everything is `IF NOT EXISTS`, so the schema is idempotent on restart. There is **no migration mechanism**: adding a column to an existing table requires an `ALTER TABLE ... ADD COLUMN` run manually or added after `exec(SCHEMA)` (guarded by a `PRAGMA table_info` check).
- No foreign keys are declared; integrity is by convention.
- The two `requests` indexes serve the query page (`ctf_id` + time order) and the student detail view (`ctf_id` + `student`).

### Constructor

```js
// lines 44-66
class Db {
  constructor(file) {
    this.file = file;
    if (file !== ':memory:') fs.mkdirSync(path.dirname(file), { recursive: true });
    this.db = new DatabaseSync(file);
    this.db.exec('PRAGMA journal_mode = WAL; PRAGMA synchronous = NORMAL; PRAGMA temp_store = MEMORY;');
    this.db.exec(SCHEMA);
    this.pending = [];
    this.pendingAlerts = [];
    this.flushTimer = null;
    this.stmts = {
      insertReq: this.db.prepare(`INSERT INTO requests (ctf_id, ts, player_id, student, raw_name, source, ip, method, path, endpoint, object_id, status, size, latency, severity, flags, attacks, owner, ua, body)
        VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?)`),
      insertAlert: this.db.prepare('INSERT INTO alerts (ctf_id, ts, level, type, student, ip, msg, data) VALUES (?, ?, ?, ?, ?, ?, ?, ?)'),
      findIdentity: this.db.prepare('SELECT player_id FROM identities WHERE kind = ? AND value = ?'),
      upsertIdentity: this.db.prepare(`INSERT INTO identities (player_id, kind, value, ctf_id, first_seen, last_seen) VALUES (?, ?, ?, ?, ?, ?)
        ON CONFLICT(kind, value) DO UPDATE SET last_seen = excluded.last_seen, ctf_id = excluded.ctf_id`),
      insertPlayer: this.db.prepare('INSERT INTO players (name, created_at) VALUES (?, ?)'),
      getKv: this.db.prepare('SELECT v FROM kv WHERE k = ?'),
      setKv: this.db.prepare('INSERT INTO kv (k, v) VALUES (?, ?) ON CONFLICT(k) DO UPDATE SET v = excluded.v'),
    };
    this.ctfId = null;
  }
```

- `DatabaseSync` is synchronous: every call blocks the event loop. That is why the hot path (requests, alerts) is batched and everything else is kept small.
- PRAGMAs: WAL lets the dashboard's reads proceed while a batch is being written; `synchronous = NORMAL` trades a tiny durability window on power loss for speed; `temp_store = MEMORY` keeps sort/temp tables in RAM.
- The hot statements are prepared once. Other queries use `this.db.prepare(...)` inline each call, which is fine for their frequency.
- `upsertIdentity` on conflict updates only `last_seen` and `ctf_id`, **never** `player_id`: an identity value stays with the first player it was bound to.
- `ctfId` starts `null`; until `openCtf()` runs, `addRequest()`/`addAlert()` drop everything.

### CTF lifecycle

```js
// lines 69-97
  activeCtf() {
    return this.db.prepare('SELECT * FROM ctfs WHERE ended_at IS NULL AND imported = 0 ORDER BY id DESC LIMIT 1').get() || null;
  }
  openCtf(name) {
    let ctf = this.activeCtf();
    if (ctf && name && ctf.name !== name) {
      this.endCtf(ctf.id);
      ctf = null;
    }
    if (!ctf) {
      const r = this.db.prepare('INSERT INTO ctfs (name, started_at) VALUES (?, ?)').run(name || `ctf-${new Date().toISOString().slice(0, 10)}`, Date.now());
      ctf = this.db.prepare('SELECT * FROM ctfs WHERE id = ?').get(r.lastInsertRowid);
      log('info', `db: new CTF #${ctf.id} "${ctf.name}"`);
    }
    this.ctfId = ctf.id;
    return ctf;
  }
  endCtf(id) {
    if (!id) return;
    this.flush();
    this.db.prepare('UPDATE ctfs SET ended_at = ? WHERE id = ? AND ended_at IS NULL').run(Date.now(), id);
    if (this.ctfId === id) this.ctfId = null; // nothing is recorded until a CTF is opened again
  }
  listCtfs() {
    return this.db
      .prepare(`SELECT c.*, (SELECT COUNT(*) FROM requests r WHERE r.ctf_id = c.id) AS requests, (SELECT COUNT(*) FROM alerts a WHERE a.ctf_id = c.id) AS alerts,
        (SELECT COUNT(DISTINCT student) FROM requests r WHERE r.ctf_id = c.id) AS students FROM ctfs c ORDER BY c.id DESC`)
      .all();
  }
```

- `openCtf(name)` is called once at startup (`server.js` line 44) and by `newCtf()`. Semantics: reuse the active CTF unless a different name is given; with no name and no active CTF, create one named by today's date. Restarting the server therefore **continues** the previous CTF rather than starting a new one — by design, so a crash does not split the recording.
- `endCtf()` flushes first so no pending rows are lost, then closes the record only if still open, and if it was the active one stops recording (`ctfId = null`). `server.js stopCtf()` relies on this: after Stop, requests are proxied but not stored until a target is picked or New CTF is pressed.
- `listCtfs()` uses three correlated subqueries per row; with a handful of CTFs this is instant, with hundreds of CTFs and millions of rows it would be slow (the `COUNT(DISTINCT student)` has no covering index).

### Players and identities

```js
// lines 100-124
  playerFor(identities, displayName, ts) {
    // identities: [{kind, value}] in order of trust (gate name, app username, ip)
    let playerId = null;
    for (const { kind, value } of identities) {
      if (!value) continue;
      const row = this.stmts.findIdentity.get(kind, value);
      if (row) {
        playerId = row.player_id;
        break;
      }
    }
    if (!playerId) {
      playerId = Number(this.stmts.insertPlayer.run(displayName, ts).lastInsertRowid);
    }
    for (const { kind, value } of identities) if (value) this.stmts.upsertIdentity.run(playerId, kind, value, this.ctfId, ts, ts);
    return playerId;
  }
  playerHistory(playerId) {
    const ids = this.db.prepare('SELECT kind, value, ctf_id, first_seen, last_seen FROM identities WHERE player_id = ? ORDER BY last_seen DESC').all(playerId);
    const ctfs = this.db
      .prepare(`SELECT c.id, c.name, c.started_at, COUNT(r.id) AS requests, SUM(CASE WHEN r.flags LIKE '%idor-success%' THEN 1 ELSE 0 END) AS idor
        FROM requests r JOIN ctfs c ON c.id = r.ctf_id WHERE r.player_id = ? GROUP BY c.id ORDER BY c.id DESC`)
      .all(playerId);
    return { identities: ids, ctfs };
  }
```

- `playerFor()` is the cross-CTF matcher. The caller (`server.js playerIdFor()`) passes identities in trust order — gate name, `gate:*` answers, app username, IP — and the **first one that already exists wins**. Then every identity in the list is upserted onto that player, so new evidence (a new IP, a new spelling of the name) accumulates.
- Consequences: two students who share an IP (same NAT, same lab machine) and never provided a stronger identity would be merged into one player by the `ip` identity. `server.js` mitigates this by not passing an `ip` identity for `source === 'ip'` lanes and by putting IP last, but the risk exists for the first student seen from a shared IP. The test `player mapping links identities across CTFs` shows the intended case: a different display name plus the same IP → same player.
- Because `upsertIdentity` never changes `player_id`, if a name already belongs to player A and an IP already belongs to player B, the lookup picks A (name first) and the IP row stays with B. No merge of players ever happens automatically.
- `lastInsertRowid` is a `bigint` or number depending on size; `Number()` normalises it.
- `playerHistory()` powers the "same person in earlier CTFs" panel: identities newest-first, and per-CTF request and IDOR-success counts (the `LIKE '%idor-success%'` scan is per player, so small).

### Batched writes

```js
// lines 127-143
  addRequest(ev) {
    if (!(ev.ctfId || this.ctfId)) return; // no active CTF: live view only
    this.pending.push(ev);
    if (this.pending.length >= 500) this.flush();
    else if (!this.flushTimer) {
      this.flushTimer = setTimeout(() => this.flush(), 200);
      if (this.flushTimer.unref) this.flushTimer.unref();
    }
  }
  addAlert(a) {
    if (!(a.ctfId || this.ctfId)) return;
    this.pendingAlerts.push(a);
    if (!this.flushTimer) {
      this.flushTimer = setTimeout(() => this.flush(), 200);
      if (this.flushTimer.unref) this.flushTimer.unref();
    }
  }
```

- Rows are queued by reference; the actual column mapping happens in `flush()`. An event may carry its own `ctfId` (tests do this) — otherwise the active one is used *at flush time*, not at queue time. In practice `endCtf()` flushes before changing `ctfId`, so this does not misattribute rows.
- Two triggers: 500 queued requests (fuzzing), or a 200 ms timer. The timer is `unref()`'d so a pending batch does not keep the process alive — which is why `close()` and every reader call `flush()` explicitly.
- Alerts share the timer but have no size trigger (they are rare).

```js
// lines 144-167
  flush() {
    clearTimeout(this.flushTimer);
    this.flushTimer = null;
    if (!this.pending.length && !this.pendingAlerts.length) return;
    const reqs = this.pending.splice(0);
    const alerts = this.pendingAlerts.splice(0);
    try {
      this.db.exec('BEGIN');
      for (const e of reqs) {
        this.stmts.insertReq.run(
          e.ctfId || this.ctfId, e.ts, e.playerId || null, e.student, e.rawName || null, e.source || null, e.ip || null, e.method, e.path,
          e.endpoint || null, e.objectId == null ? null : String(e.objectId), e.status, e.size, e.latencyMs, e.severity,
          JSON.stringify(e.flags || []), JSON.stringify(e.attacks || []), e.owner || null, e.ua || null, e.body ? JSON.stringify(e.body) : null
        );
      }
      for (const a of alerts) this.stmts.insertAlert.run(a.ctfId || this.ctfId, a.ts, a.level, a.type, a.student || null, a.ip || null, a.msg, a.data ? JSON.stringify(a.data) : null);
      this.db.exec('COMMIT');
    } catch (err) {
      try {
        this.db.exec('ROLLBACK');
      } catch {}
      log('error', `db flush failed: ${err.message}`);
    }
  }
```

- `splice(0)` empties the queues *before* writing, so a crash in the middle loses that batch (it is logged, not retried). `BEGIN`/`COMMIT` makes the batch atomic and is the main reason batching is fast (one fsync per batch instead of per row).
- The 20 positional parameters must match the column list in `insertReq` exactly; this is the place to look when adding a column. `objectId` is coerced to text, `flags`/`attacks`/`body` are JSON-encoded, `latencyMs` goes into `latency`.
- A `NOT NULL` violation (e.g. `student` undefined) fails the **whole batch** — every row in it is lost. Callers must guarantee `student`, `ts`, `ctf_id`.
- `ROLLBACK` is itself wrapped because the failure may have happened before `BEGIN` succeeded.

### Reads: alerts and ack

```js
// lines 170-186
  alerts({ ctfId, level, ack, limit = 500 } = {}) {
    const where = ['ctf_id = ?'];
    const params = [ctfId || this.ctfId];
    if (level) {
      where.push('level = ?');
      params.push(level);
    }
    if (ack === 0 || ack === 1) {
      where.push('ack = ?');
      params.push(ack);
    }
    return this.db.prepare(`SELECT * FROM alerts WHERE ${where.join(' AND ')} ORDER BY id DESC LIMIT ?`).all(...params, Math.min(Number(limit) || 500, 5000));
  }
  ackAlerts(ids) {
    const stmt = this.db.prepare('UPDATE alerts SET ack = 1 WHERE id = ?');
    for (const id of ids) stmt.run(Number(id));
  }
```

- The `WHERE` is assembled from fixed fragments only; user input enters only as parameters. `ack` is filtered only when it is exactly `0` or `1` (the dashboard passes `Number(qs.get('ack'))`).
- Newest first, hard cap 5000. The `data` column is returned as the raw JSON string; `dashboard.js` parses it (`safeJson`).
- `ackAlerts` runs one `UPDATE` per id; callers pass a few ids at a time. "Ack all" is done by `dashboard.js` with a raw statement.

### Reads: student detail

```js
// lines 187-208
  studentDetail(student, ctfId) {
    this.flush();
    const cid = ctfId || this.ctfId;
    const userAgents = this.db.prepare('SELECT ua, COUNT(*) AS n FROM requests WHERE ctf_id = ? AND student = ? GROUP BY ua ORDER BY n DESC').all(cid, student);
    const ips = this.db.prepare('SELECT ip, COUNT(*) AS n, MIN(ts) AS first, MAX(ts) AS last FROM requests WHERE ctf_id = ? AND student = ? GROUP BY ip ORDER BY n DESC').all(cid, student);
    const rows = this.db.prepare('SELECT * FROM requests WHERE ctf_id = ? AND student = ? ORDER BY id DESC LIMIT 5000').all(cid, student);
    const attacks = {};
    for (const r of rows) {
      let list = [];
      try {
        list = JSON.parse(r.attacks || '[]');
      } catch {}
      for (const a of list) {
        const k = a.cls || a;
        attacks[k] = attacks[k] || { count: 0, samples: [] };
        attacks[k].count++;
        if (attacks[k].samples.length < 25) attacks[k].samples.push({ id: r.id, ts: r.ts, method: r.method, path: r.path, status: r.status, where: a.where, sample: a.sample });
      }
    }
    const player = this.db.prepare('SELECT player_id FROM requests WHERE ctf_id = ? AND student = ? AND player_id IS NOT NULL LIMIT 1').get(cid, student);
    return { student, userAgents, ips, attacks, requests: rows.map(parseRow), player: player ? this.playerHistory(player.player_id) : null, playerId: player ? player.player_id : null };
  }
```

- `flush()` first, so the detail view includes requests from the last 200 ms.
- Three aggregate queries (UAs, IPs, latest 5000 rows). The attack summary is computed in JS over those rows: count per class and up to 25 newest samples per class. `a.cls || a` tolerates a legacy format where `attacks` was an array of strings.
- The player link is taken from any row with a `player_id`; anonymous lanes have none and get `player: null`.
- With `ctfId` 0/undefined and no active CTF, `cid` is `null` and every query returns nothing — the dashboard passes `scopeCtf(...) || 0` so this is the "no CTF" case, not an error.


- `sql` is **not** user text: it is the output of `query.js compile()`, which only ever emits column names from its own `FIELDS` table and `?` placeholders. The only interpolated value is the numeric limit, forced through `Number()` and capped at 20 000. Do not pass anything else into `runSql`.

```js

  exportCtf(ctfId) {
```

- The export is a plain JSON document with a `format` tag. Requests are parsed (`flags`, `attacks`, `body` become real arrays/objects) so the file is readable; alerts are raw rows. Players are exported as one row per identity (a join), informational only — `importCtf` does not read them.
- The entire CTF is materialised in memory; `dashboard.js` streams it as one JSON response.


- The imported CTF gets a fresh id, `imported = 1` (so it can never become the active CTF) and both timestamps filled (so it is listed as ended).
- Rows accept both column spelling (`raw_name`, `object_id`, `latency`) and event spelling (`rawName`, `objectId`, `latencyMs`), so an export and a hand-made JSONL-derived file both work. `player_id` is always `NULL`: players are per-installation and are not imported.
- Alerts default to level `medium` when missing; `data` is passed through if it is already a string (export rows) or encoded if it is an object.
- **Gotcha:** the `ctfs` insert happens *before* `BEGIN`. If a request row violates `NOT NULL` (e.g. missing `student`), the transaction rolls back and the error propagates, but the empty `(imported)` CTF row remains in the list.

### Accounts and sessions

```js
// lines 249-274
  replaceAccounts(list) {
    this.db.exec('DELETE FROM sessions; DELETE FROM accounts;');
    const stmt = this.db.prepare('INSERT INTO accounts (username, pass_hash, role, created_at) VALUES (?, ?, ?, ?)');
    for (const a of list) stmt.run(a.username, a.passHash, a.role, Date.now());
  }
  account(username) {
    return this.db.prepare('SELECT * FROM accounts WHERE username = ?').get(username) || null;
  }
  accountById(id) {
    return this.db.prepare('SELECT id, username, role FROM accounts WHERE id = ?').get(id) || null;
  }
  activeSession(accountId, ttlMs) {
    return this.db.prepare('SELECT * FROM sessions WHERE account_id = ? AND last_seen > ? ORDER BY last_seen DESC LIMIT 1').get(accountId, Date.now() - ttlMs) || null;
  }
  createSession(tokenHash, accountId, ip) {
    this.db.prepare('DELETE FROM sessions WHERE account_id = ?').run(accountId);
    this.db.prepare('INSERT INTO sessions (token_hash, account_id, ip, created_at, last_seen) VALUES (?, ?, ?, ?, ?)').run(tokenHash, accountId, ip, Date.now(), Date.now());
  }
  session(tokenHash, ttlMs) {
    const s = this.db.prepare('SELECT * FROM sessions WHERE token_hash = ? AND last_seen > ?').get(tokenHash, Date.now() - ttlMs);
    if (s) this.db.prepare('UPDATE sessions SET last_seen = ? WHERE token_hash = ?').run(Date.now(), tokenHash);
    return s || null;
  }
  deleteSession(tokenHash) {
    this.db.prepare('DELETE FROM sessions WHERE token_hash = ?').run(tokenHash);
  }
```

- `replaceAccounts()` wipes **all** sessions and accounts: `auth.js generateAccounts()` calls it at every server start, which is why the credentials are reprinted on each boot and every dashboard user must log in again.
- `accountById()` deliberately omits `pass_hash` — it is what gets attached to `req.user`.
- `createSession()` deletes the account's other sessions first: one live session per account. `auth.js` uses `activeSession()` *before* `createSession()` to detect "someone else is already logged in as this user from another IP" and raise the critical `admin-login-conflict` alert.
- `session()` is a sliding-expiry lookup: each successful check bumps `last_seen`. The TTL is `SESSION_TTL_HOURS` (default 12 h).
- Expired sessions are never deleted; they just stop matching. The table stays tiny because of the one-per-account rule.

### Key/value and close

```js
// lines 277-293
  get(k, fallback) {
    const r = this.stmts.getKv.get(k);
    if (!r) return fallback;
    try {
      return JSON.parse(r.v);
    } catch {
      return fallback;
    }
  }
  set(k, v) {
    this.stmts.setKv.run(k, JSON.stringify(v));
  }

  close() {
    this.flush();
    this.db.close();
  }
```

- `get()` returns the fallback for a missing key **and** for unparsable JSON. `set()` upserts. Values are whole documents: `admin.js` rewrites its full state object on every change.
- `close()` flushes first; `server.js shutdown()` calls it on SIGINT/SIGTERM.

### `parseRow`

```js
// lines 296-306
function parseRow(r) {
  const out = { ...r };
  for (const k of ['flags', 'attacks', 'body']) {
    if (typeof out[k] === 'string') {
      try {
        out[k] = JSON.parse(out[k]);
      } catch {}
    }
  }
  return out;
}
```

Turns the three JSON text columns back into values on the way out (`runSql`, `studentDetail`, `exportCtf`, `requestsOf`). On a parse failure the string is left as-is, which is why `replay.js` checks `Array.isArray`.
